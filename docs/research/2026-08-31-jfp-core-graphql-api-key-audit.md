# JFP Core GraphQL API — does a partner need an API key?

A one-off, code-grounded audit answering an external partner's question: "do we need an API key to use the JFP Core GraphQL API?" Written 2026-08-31 against `helm/open-graphql` (branch tip at the time of writing).

**Where this lives:** neither `docs/residual-review-findings/` (tied to one code-review run against one branch/plan) nor `docs/solutions/` (each entry there is a single fixed bug with a `root_cause`/`resolution_type` writeup) fit a standalone, multi-service audit like this one. `docs/solutions/security-issues/` came closest, but its two existing entries are both post-hoc "we found and fixed this bug" writeups, and two findings below (the Flags) are _not yet fixed_. Created `docs/research/` as a new location for this kind of one-off investigative deliverable. If more research writeups accumulate here, revisit whether they belong in `docs/solutions/` instead once there's a fix to record.

## Findings reviewed — both accepted, no action taken

Two things surfaced during this audit that technically allow unauthenticated reads beyond the intended public catalog. Neither is what the partner asked about. Both were reviewed with Tanner Fleming on 2026-09-01 and accepted as-is — recorded below for visibility, not as an open action item.

### Flag 1 (accepted risk, reviewed 2026-09-01): `Query.arclightApiKeys` / `Query.arclightApiKeyByKey` expose every partner's raw API key

**`Query.arclightApiKeys` and `Query.arclightApiKeyByKey` on the public GraphQL gateway have no authentication or authorization check at all.** Any caller — no JWT, no interop token, no API key, nothing — can run this against the public gateway endpoint and get back **every legacy Arclight partner API key in the database, in plaintext, plus its description and default platform**:

```graphql
{
  arclightApiKeys {
    key
    desc
    defaultPlatform
  }
}
```

- Defined with no `.withAuth(...)` wrapper: `apis/api-media/src/schema/arclightApiKey/arclightApiKey.ts:33-54`. Verified directly by reading the file — no auth call anywhere in it.
- Confirmed present on the public composed supergraph schema with no restricting directive: `apis/api-gateway/schema.graphql:1643-1644`.
- The `api-media` Pothos builder configures no default/fallback auth scope at all (`apis/api-media/src/schema/builder.ts:73-127`) — Pothos ScopeAuth here is opt-in per field, so an omitted `.withAuth(...)` call means the field is world-readable, not "secure by default." This same allow-by-default pattern holds across all five subgraphs.
- Every comparable admin/list field elsewhere in `api-media` is wrapped in `t.withAuth({ isPublisher: true })` — e.g. `adminVideo`/`adminVideos` (`apis/api-media/src/schema/video/video.ts:497,519`), every video mutation (`videoCreate`, `videoUpdate`, `videoDelete` — same file, lines 658/733/967). This field's lack of a guard is inconsistent with the rest of the codebase's pattern, not a documented exception.
- This is **not** the same issue as "Arclight's REST façade doesn't enforce its API key" (see §5) — that is a _documented, longstanding, intentional_ design choice (the key there is a config handle, not a secret, per `apps/arclight/CONTEXT.md:45-47`). This GraphQL leak is different: it hands out the literal key _values_ that back that config handle, unauthenticated, from a service that gates every comparable field. It has existed since the field was introduced in commit `5a50859c8` ("feat: add arclight apikey to backend (#6669)", 2025-05-15, Tanner Fleming) — confirmed via `git log --follow -p` that the file's content is byte-identical from that commit to today; it was never guarded and nothing was ever removed. Not a regression — but not intentional either (no comment, test, or doc anywhere describes these two fields as meant to be public).
- **Impact**: the leaked `key` values only function as an identity/config lookup on Arclight's REST endpoints (§5 — they were never an access-control secret there), so this does not by itself unlock additional _content_. The real harm is (a) it lets anyone enumerate every named distribution partner and their key in one request — a partner-confidentiality/business-relationship leak, and (b) it forecloses ever making the key load-bearing for auth later, since it's already public.
- **Original recommendation**: wrap both fields in `t.withAuth({ isPublisher: true })`, matching the rest of `api-media`'s admin surface. `arclightApiKeys` (the list-all field) has no legitimate consumer in this repo today — only `arclightApiKeyByKey` (singular) is called, and only server-side from `apps/arclight/src/lib/getPlatformFromApiKey.ts:8-14`.
- **Disposition (2026-09-01, Tanner Fleming): accepted, no fix planned.** These keys are not access-control secrets (confirmed in §5) — the only residual exposure is partner enumeration, which is not considered a risk worth gating. Left open by design.

### Flag 2 (accepted risk, reviewed 2026-09-01): `Query.journey` has no default status filter — draft/trashed journeys are fetchable with zero credentials if the id or slug is known

**`Query.journey` on `api-journeys` has no `.withAuth(...)` wrapper, and unlike its sibling `Query.journeys`, it applies no default status filter** — `apis/api-journeys/src/schema/journey/journey.query.ts:14-95`. Verified directly:

```ts
if (options.status != null && options.status.length > 0) {
  filter.status = { in: options.status as PrismaJourneyStatus[] }
}
```

(`journey.query.ts:78-82`) — the `status` filter is applied **only if the caller explicitly requests it**. An anonymous caller who omits `options.status` (the common case — this is how every public "view a published journey" call already works) gets whatever status the row is actually in: `draft`, `archived`, `trashed`, or `published`. The only gating that exists is unrelated to status — a custom-domain/team routing filter (`journey.query.ts:52-72`) that restricts which _hostname_ a journey resolves under, not whether it's published.

Contrast with `Query.journeys` (plural, the browse/template-gallery query), which hard-filters `status: JourneyStatus.published` unconditionally (`apis/api-journeys/src/schema/journey/journeys.query.ts:27`) — the singular query was evidently meant to have the same protection and doesn't.

- **Impact**: anyone who can guess or obtain a journey's `id`/`slug` (e.g. from a shared draft link, a leaked preview URL, or brute-forcing short slugs) can fetch its full content — blocks, actions, team association — with zero credentials, regardless of whether the creator ever published it or later trashed it. This is lower severity than Flag 1 (requires already knowing/guessing an identifier, and journeys are evangelism-content rather than PII), but it is a genuine confidentiality gap for draft/unpublished ministry content and not how the equivalent plural query behaves. The `Journey.title` field is even documented in its own schema description as _"private title for creators"_ (`apis/api-journeys/src/schema/journey/journey.ts:33-36`) — and the full `blocks` field (`journey.ts:63`) is exposed too, so this is not just metadata.
- **Checked and ruled out as a secondary path**: the `userJourneys` sub-relation on `Journey` (which would otherwise let this chain into leaking who has access to a journey) self-restricts in its own resolver — it returns `[]` for a non-`authenticated` context and, even for an authenticated caller, only the journeys _they_ already have team/ownership access to (`apis/api-journeys/src/schema/journey/journey.ts:247-296`). So this finding is scoped to a journey's own content, not to leaking other users' roles.
- **Not a regression — inherited unchanged from the pre-migration legacy resolver.** `git show f29f549bd^:apis/api-journeys/src/app/modules/journey/journey.resolver.ts` (the NestJS implementation removed in `f29f549bd`, "chore: remove legacy api-journeys service code (#9288)") shows the _exact same_ logic: no `@UseGuards` on this resolver method, unlike ~10 sibling mutations in the same file that all carry `@UseGuards(AppCaslGuard)`, and an identical conditional status-filter. The Pothos rewrite ported this behavior byte-for-byte; it was not introduced or weakened during the api-journeys-modern migration. It also isn't documented as intentional anywhere found — contrast with `apis/api-journeys/CONTEXT.md`, which explicitly notes the Template Gallery Page's public type is deliberately narrowed "so anonymous callers cannot traverse to team or block internals," showing the team is normally deliberate about this exact class of leak elsewhere.
- **Original recommendation**: apply the same default `status: published` (or an explicit `t.withAuth` + ACL check when no status is requested) to the singular `journey` query that `journeys` already has (`apis/api-journeys/src/schema/journey/journeys.query.ts:27`, unconditional `status: JourneyStatus.published`).
- **Disposition (2026-09-01, Tanner Fleming): accepted, no fix planned.** This is intentional — it's what makes it possible to share a not-yet-published journey by link (e.g. for review/preview) before hitting Publish. Not a bug.

No other unauthenticated-read findings were identified in this audit's scope. Everything else below is either working as designed or a lower-severity architectural note.

## Plain-language summary (for the partner)

**Short answer: no, you do not need an API key to read public video/media catalog data from the JFP Core GraphQL API — but "the GraphQL API" and "Arclight" are two different things, and it matters which one you're integrating with.**

The main public GraphQL endpoint (reachable at the gateway) is open by design: anyone can query it, and most of what it returns — video titles, descriptions, streaming URLs, available languages, countries — is intentionally public catalog data, the same information visible on the public website. You can query it today with no credentials and no signup. There is no API key issued for this endpoint, and it wouldn't currently do anything if you had one — every public field ignores it.

Separately, there is a legacy REST API called "Arclight" (`api.arclight.org` / `arc.gt`), built years ago for older third-party apps to consume the same catalog in a different format. It historically accepted an `apiKey` query parameter, and some partners were issued one. In the current codebase, that key has never actually been required or checked — it only changes small presentation details (which app platform's URL shape you get back), and if you omit it the API quietly falls back to sensible defaults. So functionally, Arclight is also open today, and has been since this generation of the service was built.

One thing is worth being upfront about: some parts of the platform genuinely do require credentials — anything that lets someone log in, see a specific person's private data, or edit/delete/create content requires a real Firebase-based login and, for admin-style actions, a specific internal role; none of that is reachable by an outside partner without us granting them an account. This review also surfaced two lower-severity findings, both reviewed and accepted as intentional rather than fixed: a GraphQL field that lets anyone list out legacy Arclight partner keys (those keys were never security-sensitive to begin with — see below), and a query that can return an unpublished/draft journey if someone already has its link (which is intentional — it's how a draft journey gets shared for preview before publishing). Neither is a new problem, and neither changes the answer to "do you need a key for the public catalog."

Practically, for a partner asking "what do I send you to authenticate": nothing, for read access to the public catalog. If they eventually need something that isn't public today (write access, private data, higher rate limits, or a formal support relationship), that would need to be designed and issued specifically — it doesn't exist as a mechanism today.

## 1. Every GraphQL endpoint, and what it's served on

| Deployable                                                   | Directory            | Role                                                                                                     | Framework                          |
| ------------------------------------------------------------ | -------------------- | -------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| `api-gateway`                                                | `apis/api-gateway`   | Federation gateway — the **only** public GraphQL surface; composes all subgraphs into one supergraph     | GraphQL Hive Gateway               |
| `api-journeys` (Terraform module name `api-journeys-modern`) | `apis/api-journeys`  | Federated subgraph — journeys/blocks/teams                                                               | GraphQL Yoga + Pothos (code-first) |
| `api-languages`                                              | `apis/api-languages` | Federated subgraph — languages/countries reference data                                                  | GraphQL Yoga + Pothos              |
| `api-media`                                                  | `apis/api-media`     | Federated subgraph — video catalog, short links, Arclight API keys                                       | GraphQL Yoga + Pothos              |
| `api-users`                                                  | `apis/api-users`     | Federated subgraph — Firebase-projected user identity                                                    | GraphQL Yoga + Pothos              |
| `api-analytics`                                              | `apis/api-analytics` | Federated subgraph — thin layer over Plausible Analytics' own DB (Plausible-authenticated, not Firebase) | GraphQL Yoga + Pothos              |

All six are true GraphQL servers, but **only `api-gateway` is meant to be reached directly by an external caller, and it is the only one actually network-reachable from the internet.** The other five are Federation 2 subgraphs — they speak GraphQL over HTTP, but their schemas are designed to be composed, not called standalone by outside clients (`apis/AGENTS.md:1-8`, `apis/api-gateway/CONTEXT.md:9-11`) — and confirmed at the infrastructure level: each subgraph's own Terraform locals set `is_public = false` (`apis/api-media/infrastructure/locals.tf:52`, `apis/api-journeys/infrastructure/locals.tf:65`, `apis/api-languages/infrastructure/locals.tf:22`, `apis/api-users/infrastructure/locals.tf:20`, `apis/api-analytics/infrastructure/locals.tf:10`), while `api-gateway` and `apps/arclight` both set `is_public = true` (`apis/api-gateway/infrastructure/locals.tf:14`, `apps/arclight/infrastructure/locals.tf:21`). This flag is what routes each service onto the internal vs. public AWS ALB in `infrastructure/environments/prod/main.tf`.

**Route/mount path**: every subgraph and the gateway mount their Yoga/Hive-Gateway server at `graphqlEndpoint: '/'` (`apis/api-gateway/src/common.config.ts:15`) — i.e. `POST /` is the GraphQL endpoint on each service; there is no `/graphql` suffix convention here. The gateway additionally exposes `/health` (`apis/api-gateway/src/common.config.ts:16`); each subgraph exposes `/.well-known/apollo/server-health` (e.g. `apis/api-media/src/yoga.ts:73-77`).

**Arclight and Watch — what they actually are:**

- **Arclight** is a _separate, non-GraphQL_ product: `apps/arclight` is a Hono-based REST façade replicating the response shapes of the historical `api.arclight.org` API for legacy third-party consumers. It has its own deployable (Terraform module `arclight`) and its own public hostnames — `core.arclight.org`, `arclight.org`, `*.arclight.org`, `arc.gt`, `*.arc.gt` (`infrastructure/environments/prod/main.tf:110-123`). It has no GraphQL endpoint of its own; internally it calls the `api-gateway` GraphQL endpoint as a client (`apps/arclight/src/lib/getPlatformFromApiKey.ts:1-84` uses `getApolloClient()` to query the gateway). "Arclight" in `apis/api-media`'s schema (the `ArclightApiKey` type, `Platform.arclight` enum value, `restrictViewPlatforms`) is just the media catalog's awareness of that consuming surface — it owns no separate data model (`CONTEXT-MAP.md:13`, `CONTEXT-MAP.md:63`).
- **Watch** is the public `/watch` video-library section of `jesusfilm.org`, currently implemented by `apps/resources` (the legacy `apps/watch`/`apps/watch-modern` were removed from the repo — `CONTEXT-MAP.md:76`). It's a normal web frontend that calls the public `api-gateway` GraphQL endpoint like any other first-party client; `Platform.watch` is one of three enum values (`arclight`, `journeys`, `watch`) media content can be restricted to/from (`apis/api-media/CONTEXT.md`, "Distribution & access → Platform"). It has no API-key mechanism of its own — it's just a browser hitting the public gateway.
- `workers/jf-proxy` (a Cloudflare Worker) is pure edge routing (`/watch*` → the Watch destination, `/journeys*`/`/resources` → the Resources destination) — it calls the gateway's public GraphQL endpoint for one lookup (slug resolution, `workers/jf-proxy/src/resolveWatchRedirect.ts:58-99`) but performs no auth of its own; it's a routing shim, not an API-key boundary.

## 2. What auth is actually enforced, per endpoint

**Architecture (common to all six services, confirmed by reading each `yoga.ts`/`gateway.config.ts` directly, not from docs):**

- The **gateway is the single JWT-verification point.** It validates a Firebase `Authorization: JWT <token>` header against Google's JWKS (RS256) — `apis/api-gateway/src/common.config.ts:35-59`. **A missing token is explicitly allowed through**: `reject: { missingToken: false }` (`apis/api-gateway/src/common.config.ts:63-65`), confirmed in prose by the gateway's own `CONTEXT.md`: _"A missing token is allowed; queries proceed anonymously."_ (`apis/api-gateway/CONTEXT.md`, "Caller Identity"). This is allow-by-default at the transport layer, by design — auth is enforced per-field downstream, not at the door.
- The gateway forwards the _decoded, unverified_ JWT payload plus an **HMAC signature** to each subgraph (`hmacSignature: { secret: process.env.GATEWAY_HMAC_SECRET }`, `apis/api-gateway/src/common.config.ts:32-34`).
- Every subgraph's `yoga.ts` runs `useHmacSignatureValidation({ secret: ... })` in every environment except `test` (e.g. `apis/api-media/src/yoga.ts:74-78`). This means a subgraph **rejects any request that didn't pass through the gateway with a valid signature** — so even though subgraphs are network-internal (see §3), they also can't be called with a forged/absent gateway signature even from inside the VPC.
- Each subgraph then builds a `Context` from the forwarded JWT payload (`getUserFromPayload`), an `interop-token` header for trusted service-to-service calls (`getInteropContext`), or falls through to `type: 'public'` if neither is present — e.g. `apis/api-media/src/yoga.ts:33-67`, `apis/api-journeys/src/yoga.ts:34-66`, `apis/api-languages/src/yoga.ts:32-71`, `apis/api-users/src/yoga.ts:23-43`.
- Field-level authorization is via **Pothos's ScopeAuth plugin**, configured per subgraph (`apis/api-journeys/src/schema/builder.ts:75-77`, `apis/api-media/src/schema/builder.ts:90-…`, `apis/api-languages/src/schema/builder.ts`, `apis/api-users/src/schema/builder.ts`, `apis/api-analytics/src/schema/builder.ts:57-63`). **Important architectural fact: none of the five subgraphs configure a scope-auth fallback/default.** Pothos ScopeAuth's default behavior is that a field with no `.withAuth(...)` wrapper is **open to any caller who can reach the resolver**, including the fully anonymous `'public'` context. This is _allow-by-default_, not deny-by-default — there is no catch-all "require at least X" rule; every field's exposure is an individual, per-field decision by whoever wrote it. That's a legitimate design for a public content catalog, but it means correctness depends entirely on nobody forgetting a `.withAuth(...)` call — which is exactly what happened in the Flag 1 finding above.

**Per-subgraph specifics:**

- **`api-users`**: Firebase JWT → `Context.currentUser`; roles resolved from `prisma.user.findUnique(...).superAdmin` per request (`apis/api-users/src/schema/builder.ts:73-90`). The two highest-sensitivity mutations are both correctly gated:
  - `userImpersonate` (superAdmin obtains a token to act as another user, by email) — `t.withAuth({ isSuperAdmin: true })`, `apis/api-users/src/schema/user/user.ts:203-221`.
  - `userDeleteCheck`/`userDeleteConfirm` (account deletion) — `t.withAuth({ isAuthenticated: true })` at the field level, **plus** an explicit in-resolver check that a non-superAdmin caller can only target themselves: `if (!caller.superAdmin && targetUserId !== ctx.currentUser.id) throw Forbidden` — `apis/api-users/src/schema/userDelete/userDeleteCheck.ts:76-85`, `apis/api-users/src/schema/userDelete/userDeleteConfirm.ts:75-87`.
  - `user`/`userByEmail` (look up any user by id/email) — gated `isValidInterop: true` only, i.e. **not** callable by an ordinary authenticated end user, only by trusted server-to-server callers via the interop token — `apis/api-users/src/schema/user/user.ts:175-199`.
  - Minor, sub-flag-level note: `validateEmail(email, token)` has no `.withAuth()` and distinguishes `"User not found"` from `"Invalid token"` in its error (`apis/api-users/src/schema/user/user.ts:246-271`) — a standard email-verification-link pattern (the token is the real credential), but it does let an anonymous caller check whether a given email address has an account. Low severity, noted for awareness, not treated as a third Flag.
- **`api-languages`**: all writes (`languageUpdate`, `languageNameUpdate`, `countryLanguageCreate/Update/Delete`, `audioPreviewCreate/Update/Delete`, `wessImport`) and the two admin reads (`adminLanguages`, `adminLanguagesCount`) are `t.withAuth({ isPublisher: true })` — confirmed by grepping every `queryFields`/`mutationFields` block in the subgraph (`apis/api-languages/src/schema/{language,country,countryLanguage,wessImport}/*.ts`). Public reads (`language`, `languages`, `languagesCount`) have no auth and are intentionally public reference data (`apis/api-languages/src/schema/language/language.ts:149-237`) — the plural forms force `hasVideos: true` so unpublished/no-video languages are excluded from bulk listing; the singular `language(id)` lookup does not apply that filter, a minor inconsistency but not a PII/security issue since it's still just language metadata (name, codes), never anything user-identifying. Separately: `AuthenticatedUser.languageUserRoles`, a federation extension field this subgraph adds to the shared `AuthenticatedUser` type, has no `.withAuth()` either (`apis/api-languages/src/schema/user/user.ts:22-34`) — but every entry point to an `AuthenticatedUser` object found in this audit (`me` on `api-users`, and `UserJourney`/`UserTeam`/`Integration.user` on `api-journeys`) already requires the caller to be authenticated and scoped to their own data or a journey/team they legitimately have access to, so no anonymous cross-user read was found in practice. Worth a `.withAuth()` anyway for defense-in-depth, since the guarantee currently depends entirely on every _other_ field in the graph, not this one.
- **`api-media`**: every video-catalog mutation and every admin-prefixed read (`adminVideo`, `adminVideos`, `adminVideosCount`, `restrictViewPlatforms`, `restrictDownloadPlatforms`, `videoCreate/Update/Delete`, `videoImageAlt*`, `videoDescription*`, `videoStudyQuestion*`, etc.) is `t.withAuth({ isPublisher: true })` (`apis/api-media/src/schema/video/video.ts:403-1087`, and siblings). Public catalog reads (`video`, `videos`, `videosCount`) have no auth by design — this is the public video catalog. `shortLinkByPath` (used by the public Short Links redirect surface to resolve a hostname+path to a destination) is intentionally unauthenticated (`apis/api-media/src/schema/shortLink/shortLink.ts:65-102`); the id-based `shortLink` lookup and all `shortLinkDomain*`/mutation fields require `isPublisher`/`isValidInterop`/`isAuthenticated` (`apis/api-media/src/schema/shortLink/shortLink.ts:103-134`, `apis/api-media/src/schema/shortLink/shortLinkDomain/shortLinkDomain.ts:44-227`). **The one exception found is `arclightApiKeys`/`arclightApiKeyByKey` — see Flag 1.**
- **`api-analytics`**: exposes exactly one write, `siteCreate`, and no reads at all (per its own `CONTEXT.md:3`: _"It exposes one write and no reads."_). It authenticates a **Plausible identity** — not Firebase — resolved from the raw `authorization: Bearer <key>` header (the gateway forwards this header verbatim to `api-analytics` only, `apis/api-gateway/src/common.config.ts:26-27`). Validation is real: the key's 6-char prefix is looked up, then its full value is SHA-256-hashed with `PLAUSIBLE_SECRET_KEY_BASE` and compared against the stored hash; a missing/wrong key resolves to `undefined` currentUser (`apis/api-analytics/src/lib/auth/auth.ts:1-28`), and `siteCreate` is wrapped `t.withAuth({ isAuthenticated: true })` (`apis/api-analytics/src/schema/site/siteCreate.mutation.ts:17`), so an invalid/absent key is correctly rejected — this is a genuinely-enforced credential, just a different one (Plausible's, not Firebase's, not a JFP-issued key).
- **`api-journeys`**: `authScopes.ts` defines `isAuthenticated`, `isAnonymous` (has a Firebase session but no email), `isPublisher`, `isSuperAdmin` (lazily re-checked against the users DB per call), `isValidInterop`, plus per-domain functions `isInTeam`/`isTeamManager`/`isIntegrationOwner` (`apis/api-journeys/src/schema/authScopes.ts:1-135`). Team/journey access additionally goes through function-based ACLs in `*.acl.ts` files, not just coarse scopes (per `apis/AGENTS.md:296-298`, confirmed present as e.g. `journeyAcl` referenced in `apis/api-journeys/CONTEXT.md`). Authoring/admin fields checked (`adminJourney`, `block`) are correctly gated via `t.withAuth({ $any: {...} })` plus a `journeyAcl`/CASL `ability` resolver-level check (`apis/api-journeys/src/schema/journey/adminJourney.query.ts:12,42`, `apis/api-journeys/src/schema/block/block.query.ts:16,26-36`). **One public-by-design field, `journey(id, idType)`, is missing the status filter its sibling `journeys` applies — see Flag 2.**

**No global default-deny exists anywhere in this stack** — this is worth stating plainly since it's the main structural risk factor: correctness for every field, in every subgraph, rests on the author remembering to add `.withAuth(...)`. The one field that didn't (Flag 1) proves the gap is real, not theoretical.

## 3. Introspection, persisted queries, depth/complexity limiting, rate limiting

- **Introspection**: not configured anywhere. `grep -rn "introspection" apis apps/arclight --include="*.ts"` (excluding generated files) returns exactly one unrelated hit — a TypeScript type alias in `apis/api-journeys/src/lib/graphql/subgraphGraphql.ts:6`, not a server config. Neither the gateway (`apis/api-gateway/src/common.config.ts`, `gateway.config.ts`, `gateway.prod.config.ts`) nor any of the five subgraphs (`*/src/yoga.ts`) ever sets `introspection: false`. GraphQL Yoga and Hive Gateway both **default to introspection enabled**, so the full schema — including admin-only mutation names, argument shapes, and every type — is introspectable by anyone, in every environment, including production. This is reinforced by the production gateway config explicitly enabling **GraphiQL** (`graphiql: { title: '[PROD] api-gateway' }`, `apis/api-gateway/gateway.prod.config.ts:66-68`) — an interactive schema browser is reachable on the production public endpoint.
- **Persisted queries**: no `persistedQueries` configuration was found anywhere in `apis/`.
- **Depth limiting / query-complexity limiting**: none found. `grep -rin "depth-limit|querycomplexity|query-complexity"` across `apis/api-gateway`, every subgraph's `src`, and `libs/yoga` returned zero hits. No `graphql-depth-limit` or `graphql-query-complexity` package is wired into any plugin list.
- **Rate limiting**: none found at the application level (no `rate-limit`/`ratelimit`/`express-rate-limit` hits anywhere in `apis/`), and none at the infrastructure level either — `grep -rln "wafv2|aws_waf|cloudfront|rate_based" infrastructure --include="*.tf"` found no WAF or CloudFront rate-based rule attached to the public ALB, the gateway, or arclight (the one `cloudfront` hit in `infrastructure/modules/aws/datadog/main.tf` is an unrelated Datadog IAM permission, not a CDN in front of these services). The public ALB in front of `api-gateway` and `arclight` (`infrastructure/environments/prod/main.tf:18-21`) has no WAF association in this repo's Terraform.
- **Dev/stage/prod differences**: the only `NODE_ENV`-conditioned behavior found is (a) response caching being skipped in `test` (`apis/api-media/src/yoga.ts:71-92` and siblings) and (b) `useHmacSignatureValidation` being skipped in `test` so local/CI runs don't need the gateway's HMAC secret. Introspection, GraphiQL, and the absence of rate/depth/complexity limiting are **identical across dev, stage, and prod** — nothing in code turns these protections on for production.

**Net effect**: the public GraphQL surface has no request-shape guardrails at all beyond normal HTTP/infra timeouts. A single query can be arbitrarily deep or complex, and there is no throttling on request volume from any one caller, anywhere in this stack.

## 4. What's reachable with zero credentials, and what it returns

Concretely, with no `Authorization` header, no `interop-token`, and no API key, against the public `api-gateway` endpoint, all of these resolve successfully today:

- `videos` / `video(id)` / `videosCount` (`api-media`) — the full public video catalog: titles, descriptions, study questions, HLS/download URLs, subtitle tracks, per-language variants. This is the same content published on the public website; not a leak.
- `languages` / `language(id)` / `languagesCount`, `countries`/`country(id)`, `continents` (`api-languages`) — public reference data (BCP-47 tags, ISO codes, speaker counts, flags). Not sensitive.
- `shortLinkByPath(pathname, hostname)` (`api-media`) — resolves a short-link path to its destination; by design (this is what powers the public redirect surface).
- **`arclightApiKeys` / `arclightApiKeyByKey(key)` (`api-media`) — see Flag 1. Returns actual partner API-key strings. Reviewed and accepted — these keys were never access-control secrets.**
- **`journey(id, idType)` (`api-journeys`) — see Flag 2. Returns full journey content (including draft/trashed) if the caller supplies an `id`/`slug` and omits `options.status`. Reviewed and accepted — intentional, so a draft journey's link can be shared before publishing.**
- Introspection itself (`__schema`, `__type`) — the entire supergraph SDL, including every admin/mutation field name and argument shape (not the data behind them, but full API surface reconnaissance).

Everything requiring a real identity (a specific user's profile via `me`, any `adminX`/`videoCreate`-style mutation, `userImpersonate`, account deletion, Plausible site provisioning) correctly rejects an anonymous caller, per §2.

## 5. The Arclight API-key question

**Direct answer: Arclight (`apps/arclight`, the legacy REST façade) does not currently enforce its `apiKey` query parameter as an access-control credential, and — as far as this repository's git history shows — it never has.** This is not a regression; it is the documented, tested, original design.

- **Documented as intentional, not a secret**: `apps/arclight/CONTEXT.md` ("Consumers & Delivery" section): _"**API Key**: The query-string credential identifying an external consumer application. It is an identity/configuration handle (e.g. it determines the consumer's default Platform and, for some distribution partners, download-quality behavior), **not an enforced secret**."_
- **Code matches the doc, exactly**: e.g. `apps/arclight/src/app/v2/[...route]/_media-components/index.ts:26` declares `apiKey: z.string().optional()` in the request schema; nothing in that handler (or any handler grepped) ever checks it for validity or rejects a request over it — it's used only to look up a `defaultPlatform` via `getDefaultPlatformForApiKey()` (`apps/arclight/src/lib/getPlatformFromApiKey.ts:35-84`), purely to pick which URL shape to render. There is no global auth middleware on the Hono app: `apps/arclight/src/app/v2/[...route]/route.ts` wires only `compress`, `etag`, a content-type header setter, and an error handler — no auth check at any layer.
- **Git history — no evidence of removal, and evidence it was always optional**: the file history of the relevant handlers goes back to the façade's inception in 2024. The earliest commit implementing this behavior, `56104362b` ("feat: arclight facade media components calls (#3429)", 2024-09-10, Tanner Fleming), already reads `const apiKey = query.get('apiKey') ?? '616db012e9a951.51499299'` — i.e. **a missing key silently falls back to a hardcoded default key rather than rejecting**, from day one. The commit that introduced the current `getDefaultPlatformForApiKey`/`arclightApiKeyByKey`-lookup version, `adce8c814` ("feat: add platform based on apikeys (#6671)", 2025-05-15, Tanner Fleming), _replaced_ that same hardcoded-fallback pattern with the current optional-lookup pattern — a refactor of an already-non-enforcing mechanism, not a removal of enforcement. `git log --all -S'requireApiKey'` and `-S'validateApiKey'` against `apps/arclight` return **zero commits** in this repo's entire history — no such enforcement function has ever existed to be removed.
- **The one apiKey-related feature that _does_ branch behavior** is a special-case download-quality override for a specific distribution partner (`SPECIAL_API_KEY`, introduced in `595f189c2`, "feat: enhance download functionality with API key support (#7169)", 2025-07-14) — again a config/behavior fork, not an access gate.
- **The GraphQL layer's `ArclightApiKey` backing data is itself unauthenticated-readable** — that's the Flag 1 finding, and it means even if Arclight's REST layer were later changed to actually enforce the key, the key values are currently obtainable by anyone via GraphQL regardless.
- **CI/e2e coverage matches this understanding, not the "should require a key" belief**: `apps/arclight-e2e/src/e2e/media-components/index.spec.ts:234` contains a test literally named `'without apiKey still returns valid download sizes'` — the test suite actively asserts that omitting the key is fine. There is no test anywhere in `apps/arclight-e2e` that expects a 401/403 for a missing or invalid key, so **a future regression toward accidentally requiring a key would be caught by CI; a regression in the other direction (further loosening) would not be, since there's no enforcement to lose.**

**Verdict on the belief "Arclight no longer requires a key": technically it never did, in the version of this system that exists in this repository.** If an API key was ever a hard requirement, that must predate this codebase (a prior, non-JFP-core implementation of `api.arclight.org`) — nothing in this repo's history shows it being removed here.
