# Authorization service for Journeys MCP

## Decision

Use a first-party Node authorization service built on `oidc-provider`, initially pinned to **9.13.3**, released 29 October 2026. The maintained v9 line supplies the OAuth protocol machinery and fits the agreed Firebase sign-in and custom consent flow. This is an implementation recommendation from documentation and source review. Deployment and two-client acceptance remain outstanding. [Release](https://github.com/panva/node-oidc-provider/releases/tag/v9.13.3) · [Supported versions and license](https://github.com/panva/node-oidc-provider/tree/v9.13.3#supported-versions) · [Agreed architecture](https://github.com/JesusFilm/core/issues/10156)

The closest alternative is self-hosted **Ory Hydra OEL 26.4.7**. Ory documents resource indicators and automatic registration for that enterprise edition. Its current open-source release, **26.2.0**, uses a dedicated-client workaround and explicitly lacks full MCP resource-audience validation. Rule out Hydra OSS for this design. Prefer `oidc-provider` over OEL because the required protocol features are available in its MIT-licensed Node implementation, while either choice still needs our Firebase consent app and domain authorization. OEL is the fallback if the team chooses enterprise licensing and a separately operated OAuth server. [OEL guide](https://www.ory.com/docs/guides/mcp/hydra-oauth-oel) · [OSS guide](https://www.ory.com/docs/guides/mcp/hydra-oauth-oss) · [OSS release](https://github.com/ory/hydra/releases/tag/v26.2.0) · [Hydra custom login](https://www.ory.com/docs/oauth2-oidc/custom-login-consent/flow)

## MCP contract to implement

Use the **2026-07-28** authorization specification as the acceptance baseline. Publish RFC 9728 protected-resource metadata on the MCP service, including its canonical resource URI and `authorization_servers`. Provide both the well-known document and a `401` challenge with `resource_metadata`. Publish the authorization service's issuer metadata. [Discovery requirements](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery)

Support CIMD, with bounded metadata fetching and trust policy, and retain DCR for older clients plus pre-registration where needed. The current specification recommends CIMD and deprecates DCR while retaining it for compatibility. Its client preference order starts with available pre-registration, then CIMD, then DCR. Keep registrations scoped to the issuer and validate each client's redirect URIs. [Client registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)

Require PKCE S256, advertise `code_challenge_methods_supported`, use HTTPS and exact redirect validation, and rotate public-client refresh tokens. Configure client metadata fetching to reject internal destinations and unsafe redirects. [Security requirements](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)

Clients must send `resource` at authorization and token exchange. Bind each MCP token to the canonical MCP resource and validate it on every HTTP request. Emit and advertise the authorization-response `iss` parameter. Return `401` for invalid credentials and `403` for insufficient scope, with the appropriate challenge. Keep stage and production issuers, resource identifiers and registrations separate. [Authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)

## Firebase, grants and the gateway

At repository commit `593400f9201d0b2acccea67835613639619bf527`, the gateway accepts Firebase project-audience JWTs and forwards their verified payload over a signed hop. Journeys' authenticated context contains a user and current roles. Implement the delegated credential and grant context specified in #10156 across the gateway and participating services. [Gateway](https://github.com/JesusFilm/core/blob/593400f9201d0b2acccea67835613639619bf527/apis/api-gateway/src/common.config.ts#L17-L65) · [Context](https://github.com/JesusFilm/core/blob/593400f9201d0b2acccea67835613639619bf527/apis/api-journeys/src/schema/authScopes.ts#L16-L26) · [Delegation contract](https://github.com/JesusFilm/core/issues/10156)

1. Verify Firebase identity server-side in the first-party login interaction, including current account eligibility, verification and terms. Use the verified Firebase UID as the account binding. Show the client, redirect destination, actions and selected resources on consent. Firebase's default ID-token verification needs the additional revocation check when account/session revocation matters. [Firebase verification](https://firebase.google.com/docs/auth/admin/verify-id-tokens) · [Eligibility and consent requirements](https://github.com/JesusFilm/core/issues/10152)
2. Persist the provider's OAuth artifacts through a durable adapter. Link its grant ID to an application grant containing the UID, acting client, allowed operations, selected journeys or explicit team scope, expiry, version and revocation timestamp. Keep team Create independent from journey Edit. Record newly created drafts under an explicitly approved create-and-edit grant. [Adapter contract](https://github.com/panva/node-oidc-provider/blob/v9.13.3/example/my_adapter.js) · [Permission contract](https://github.com/JesusFilm/core/issues/10152)
3. Start with short-lived **opaque MCP access tokens**, authenticated introspection and a current grant lookup on every request. Bind the introspected account/client to the stored grant. The provider's JWT access tokens cannot be individually introspected or revoked through its corresponding endpoints. Opaque tokens allow its persisted-token revocation path. [Token handling source](https://github.com/panva/node-oidc-provider/blob/v9.13.3/lib/shared/reject_structured_tokens.js) · [Revocation source](https://github.com/panva/node-oidc-provider/blob/v9.13.3/lib/actions/revocation.js)
4. Have a dedicated issuer authenticate `api-mcp`, verify the MCP credential and active grant, then issue a separate short-lived gateway credential. Bind the Firebase UID, originating client, grant ID/version, allowed operations and selected resources. Restrict the issuer's signing authority and gateway audience. The external client receives only MCP credentials. The team must implement this exchange policy and gateway verifier. RFC 8693 defines the exchange protocol and leaves deployment policy to the implementation. [Token exchange](https://www.rfc-editor.org/rfc/rfc8693) · [Credential separation](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations) · [Agreed exchange](https://github.com/JesusFilm/core/issues/10156)
5. On first-party Disconnect, mark the application grant revoked durably, then revoke its OAuth artifacts. Make cleanup retryable and reject refresh or exchange against revoked grants. The gateway and owning service check the current grant and user rights before data release or commit. Jobs recheck before execution and each external delivery. Fail closed when current authorization is unavailable. A new consent gets a new grant identity. This also blocks already-issued gateway credentials after disconnect. [Adapter revocation contract](https://github.com/panva/node-oidc-provider/blob/v9.13.3/example/my_adapter.js) · [Required execution checks](https://github.com/JesusFilm/core/issues/10156)

## Two-client staging proof

Propose **Claude web custom connectors** and **VS Code's editor-managed MCP client** to meet A9's hosted-client and desktop-client requirement. Claude documents cloud-originated remote connections and OAuth. VS Code documents HTTP OAuth and CIMD. Record the test date, available version identifiers, selected runtime, negotiated MCP revision, registration method and callback shape. Verify Claude can reach the staging endpoint and that the test account can add the connector. Compatibility with this deployment still needs a staging run. [A9 requirement](https://github.com/JesusFilm/core/issues/10157) · [Claude web](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp) · [VS Code HTTP OAuth](https://code.visualstudio.com/docs/agents/reference/mcp-configuration) · [VS Code CIMD](https://code.visualstudio.com/updates/v1_106#_authentication-client-id-metadata-document-authentication-flow)

- In each client, complete discovery, registration, Firebase sign-in, resource selection, consent, tool discovery, a permitted call, refresh and disconnect. Exercise the actual CIMD/DCR or pre-registration path and PKCE failure. Confirm resource binding at both OAuth endpoints and rejection of wrong issuer, audience, expiry and cross-environment credentials. [Protocol checks](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Give one user drafts A and B. Grant the first client read/edit access only to A, and the second read-only access only to A. Deny B and the read-only client's write. Test team Create separately for a journey-only collaborator. Warm caches and repeat with a second user. Check list counts, nested fields, previews and queued results. Run the full creator workflow in both clients, including one run without optional prompts or resources. [A1 and A9 acceptance cases](https://github.com/JesusFilm/core/issues/10157)
- Revoke one grant while refresh, exchange and a queued job are pending. Prove subsequent calls and effects fail through the real gateway, including use of an already-issued gateway credential. Repeat after membership removal, account disablement and entitlement loss. Test first-party Disconnect separately from client removal and record whether removal sends a revocation request. [Execution and revocation cases](https://github.com/JesusFilm/core/issues/10156)

These checks remain unexecuted. Unit tests need additional real-configuration coverage because the shared Firebase payload helper returns a fixed user in test mode. [Test identity source](https://github.com/JesusFilm/core/blob/593400f9201d0b2acccea67835613639619bf527/libs/yoga/src/firebaseClient/firebaseClient.ts#L114-L129)
